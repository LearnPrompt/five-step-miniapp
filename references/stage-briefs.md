# 五阶段任务描述

这些是起始任务，不是必须原样粘贴的固定五次调用。已加载 Skill 时，用户只需给源码与目标。保持同一最小用户路径；完成后把结果记入 `miniapp-progress.md`，再进入下一阶段。

## 1. 做初版

阅读当前项目，说明主要功能、实际数据来源、可复用逻辑与移动端需要重排的交互。针对用户确认的最小路径，列出页面顺序和改造项；对可逆实现细节选择现有架构下的最小方案，直接实现微信小程序初版。明确源码缺项、运行入口、依赖与占位功能。

**检查：**实际运行最小路径；若只有构建或静态检查权限，保存结果并把开发工具/真机预览标记为待验证。没有 AppID 时先检查当前工具支持的本地测试方式，不虚构已绑定账号。

## 2. 调 UI

对照原项目已确认的视觉特征，检查手机屏幕上的文字、入口、点击范围、滚动和密集内容。只修改实际发现且影响使用的问题，提供同页同状态的前后对比与原因；不强行把所有网站都改成同一套布局。

**检查：**选一个真实屏幕尺寸走完主要操作；截图用于布局对比，真机操作用于触控判断。没有真机时把此项留下，继续其他可做检查。

## 3. 接数据

先追踪数据从哪里来、存在哪里、何时更新。复用可维护的后端与权限机制；缺少服务配置时给出最小接入接口并标记模拟实现，不编造云环境。按需求选择：实时读取、按日期保存、历史查询、个人收藏。每日内容的首页显示最新成功数据及实际日期；更新失败保留可用内容并记录失败，不冒充今日更新。个人数据按用户隔离，密钥不进入客户端或日志。

**检查：**用有依据的一条实际数据验证读写。定时更新需证明确实触发，数据库存在不代表更新流程成立。若使用历史/收藏，分别测试两个日期、重新进入和两个测试账号；所需账号与数据由实际环境提供。

## 4. 加 AI

围绕一个真实问题设计功能，如解释当前详情。先检查项目可用的服务端与 SDK 版本，按当前官方文档接入。基于已有资料回答，显示可核对的来源；无依据则说明不足，不补编事实。区分客户端发起、服务端请求与结果展示；设置适合现有环境的请求失败反馈。不为了“有 AI”接入无关能力。

**检查：**资料充分、资料不足、请求失败；确认引用对应输入、密钥不在客户端。只写完成代码但未调用服务时，记录“接入待验证”，不伪造输出或消耗预测。

## 5. 测试发布

先核对实际 AppID、账号可用能力、项目上传方式、服务类目、所用 AI 服务的发布条件及需要的隐私材料。仅准备当前功能所需材料，不通用假定所有账号必须企业认证，也不假定所有功能免审核。

按以下状态顺序推进，每一项留下实际结果；某项当前平台不适用则说明依据。

1. 核对后端部署、数据库权限、网络与生产配置，运行当前最小路径和本项目相关检查。失败项保存复现步骤并最小修正。
2. 在开发工具和真机验证主要功能，特别是实际数据、身份状态与外部请求；静态检查、编译和预览属于不同证据。
3. 使用项目支持的方式上传代码，记录版本号；检查可用体验版本并扫码验证。操作入口以账号当前界面为准。
4. 准备基本信息、功能说明、审核测试路径及必要材料。授权明确后提交审核并记录版本与实际状态；缺少持有人权限就指出对应操作，不自行假定已提交。
5. 审核通过且发布已获授权时，发布正式版本；从正式访问路径重新测试并记录。等待审核、驳回、未发布都停在其实际状态并列出下一步。

**发布不是截图中的按钮：**以平台状态和正式版本实际访问共同核实。不能把 WorkBuddy 或其他 Agent 自身的应用/文档发布功能当成微信小程序发布，也不能把生成代码等同于绕过微信审核。
